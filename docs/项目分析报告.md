## 2. 项目定位与整体架构

一个"由连续时间轴驱动的 3D 情绪场景"：**时间（0–24h，step 0.05）× 季节 × 天气 → 一套 20 个视觉参数（14 数值 + 6 颜色）→ 场景**。

### 2.1 单帧数据管线（实测路径，与实现逐行对齐）

```
输入 UI ──► TimeState {hour, season, weather}          src/types.ts:8
             │
             ▼  每帧全量重解析（不缓存输入）
      resolveParams(state, target)                     src/core/state.ts:39
        ├─ 采样 7 条数值轨道 + 6 条颜色轨道             src/data/seasons.ts TRACKS
        │    （锚点 = [0, 3, 日出+1, 12, 日落-1, 24=复用0] ）
        ├─ 叠加太阳几何 sunAngle()                      src/core/solar.ts
        ├─ sunInt *= daylight(elev)                     ← 地平线下强制熄灯
        ├─ 叠加天气修饰表 WEATHERS                      src/data/weather.ts:15
        └─ 派生量：lamp / ffGlow / snow                  ← 不入轨道，纯计算
             │
             ▼  指数缓动（时间常数 ≈0.42s，收敛 ~1.5s）
      lerpParams(cur, target, dt)                      src/core/state.ts:82
             │
             ▼  7 个副作用系统依次 apply()
      sky → sun → hemi → interior → vegetation
          → environment → weatherSys                   src/main.ts:77-85
             │
             ▼
      particles.update → sky.refreshEnv(脏标记+0.38s节流) → cameraSys.update
             │
             ▼
      composer.render()  (RenderPass → UnrealBloom → OutputPass)
```

### 2.2 分层职责（边界基本守住）

| 层 | 文件 | 规则遵守情况 |
|---|---|---|
| 纯函数核心 | `src/core/{state,interpolate,solar,loop}.ts` | ✅ 无 THREE 场景对象、无 DOM；仅用 `THREE.Color` 做颜色数学 |
| 数据真相 | `src/data/{seasons,weather}.ts` | ✅ 视觉常量只在这里 |
| 场景系统 | `src/systems/*.ts` | ✅ 只读 `SceneParams`，不反向改状态 |
| UI | `src/ui/hud.ts`、`style.css` | ✅ 只写 `TimeState`，不直接操作场景对象 |
| 装配 | `src/main.ts` | ✅ 唯一的"接线处" |

**值得肯定的设计（建议保持，不要在重构中丢掉）**

1. **单向数据流 + 稠密重解析**：每帧重算全部参数，没有任何"脏标记式的增量状态机"，因此不存在状态漂移类 Bug。这是本项目最大的可维护性资产。
2. **派生量不入轨道**：`lamp / ffGlow / snow / particle mode` 由 `elev` 等推出来（`state.ts:59-61`、`state.ts:93`），避免了"轨道改了但派生量没改"的双写不一致。
3. **帧循环零分配**：`createParams()` 预分配、`sampleCol` 写回 `out`（`interpolate.ts`）、`lerpParams` 原地更新、相机用 `scratch`/`sph` 复用（`camera.ts:41-42`）。GC 压力可忽略。
4. **环境贴图"脏 + 节流"**（`sky.ts:52-64`）：静止时零烘焙，这是正确的做法；`regen()` 里先 `dispose()` 旧 RT 再赋值，无 GPU 内存泄漏。
5. **自适应 DPR 同时同步 composer**（`loop.ts:49-59`，注释点明 `_pixelRatio` 构造期定型这个坑）——这是实践里很容易踩、本项目踩对的地方。
6. **可访问性不是事后补的**：`aria-live` 只挂在语境短句而非整句（`hud.ts:112-121`，避免拖动时刷屏）、`focus-visible`（`style.css:331-334`）、`prefers-reduced-motion`（418-423）、`forced-colors`（425-431）、以及 12 个对比度断言。
7. **零外部资源**：所有贴图 `systems/textures.ts` 程序化生成，无外链字体/图片/CDN；依赖精确 pin（无 `^`/`~`）。

## 4. 问题清单（按优先级）

### P0 · 确认缺陷，用户可感知

#### 4.1 时刻读数系统性少 1 分钟（`src/ui/hud.ts:19`）

```ts
const m = Math.floor((hour % 1) * 60)   // ← floor 吃掉了浮点误差
```

滑杆 `step="0.05"`（`index.html:32`），`slider.value` 序列化为最短往返字符串（`"1.15"`），但 `Number("1.15") = 1.1499999999999999`，于是 `0.1499999… × 60 = 8.9999999…`，`floor` 得 8。

**实测：481 个档位中有 182 个（37.8%）读错 1 分钟。**

| 滑杆值 | 当前显示 | 应为 |
|---|---|---|
| 1.15 | 01:08 | 01:09 |
| 1.20 | 01:11 | 01:12 |
| 1.90 | 01:53 | 01:54 |
| 2.55 | 02:32 | 02:33 |

对一个"以时间为主角"的作品，这是最容易被观众抓到的细节。修法：

```ts
const total = Math.round(hour * 60)          // 先归一到分钟再拆
const h = Math.floor(total / 60) % 24
const m = total % 60
```

**为什么测试没抓到**：`tests/hud.test.ts:11-15` 只用了 `16.5 / 18.5 / 7.5` —— 全是二进制可精确表示的值（`.5`），恰好绕开误差。补一行 `formatHour(1.15) === '01:09'` 即可。

#### 4.2 巡游按钮"撒谎"：`aria-pressed=true` 但相机不动（`src/ui/hud.ts:83-87` × `src/systems/camera.ts:80-83`）

HUD 在点击时无条件翻转 `aria-pressed`，但 `setTour()` 内部在 `prefers-reduced-motion` 下静默吞掉：

```ts
tourOn = on && !reduceMotion   // camera.ts:82
```

结果：开启"减少动态"的用户点巡游 → 按钮高亮、读屏播报"已按下"，画面纹丝不动，也没有任何提示。这是**无障碍状态下的一致性问题**，比"不支持该功能"更糟。

建议：`setTour` 返回是否真正生效，HUD 据此回填 `aria-pressed`；或在该模式下直接 `disabled` 并给出 `title/aria-description="已按系统偏好关闭自动运动"`。

#### 4.3 夜间阴影贴图空转（`src/systems/sun.ts:28-36`）

夜间太阳被夹到地平线以上（`Math.max(params.elev, 0)`，第 30 行）且方位角在夜间被 `solar.ts` 夹在 ±115° 区间内 → **阴影相机矩阵在整夜完全不变**，而 `light.castShadow = true`、`light.shadow.autoUpdate` 默认 `true`，three r160 的 `WebGLShadowMap` 只按 `castShadow/autoUpdate/needsUpdate` 决定是否绘制，**不看 `light.intensity`**。即：`intensity = 0` 的夜里，每帧仍在渲染一张 2048² 深度图（4.2 M 像素 + 全场景 draw call）。

修法（成本极低）：在 `apply()` 里按 `sunInt` 阈值切 `light.shadow.autoUpdate`（不要切 `castShadow`，那会触发材质重编译）。

#### 4.4 WebGL 失败/上下文丢失无兜底（`src/main.ts:28`、`src/main.ts:103-106`）

- `new THREE.WebGLRenderer(...)` 未包 `try/catch`：不支持 WebGL 的机器直接白屏 + 控制台异常。
- 无 `webglcontextlost` 监听：移动端切后台被回收后回来即黑屏。
- loader 的移除条件写死在"第一帧后"（`loaderDone`），一旦第一帧抛错，页面永远停在"正在构建场景 …"。

建议：`try/catch` → 显示降级文案（`<noscript>` 同理缺失）；`contextlost` 挂 `preventDefault` + `contextrestored` 重建，或至少显示重载提示。

### P1 · 体验/一致性/性能，建议排期

#### 4.5 时刻色带与场景光照"名义同源、实际不同源"（`src/ui/hud.ts:35-40`）

色带写死 `dawn 5-8 / day 8-17 / dusk 17-20`，而场景日出日落是 `solar.ts SUNRISE {6, 5.5, 6.5, 7.5} / SUNSET {18, 19, 17.5, 17}`（春/夏/秋/冬）。后果：

- 冬季 7:30 太阳还没出来，HUD 强调色已经切成"晨"；
- 冬季 17:00 已日落，HUD 还亮着"黄昏"色调直到 20:00；
- 而 `hud.ts:26` 的注释恰恰写着"与场景光照同源" —— 注释与实现不符，会误导后续维护者。

建议：`timeBand` 接受 `season`，用 `SUNRISE/SUNSET` 派生（夜晚灯泡 `lamp` 已经这么做了，`solar.ts lampLevel`）。

#### 4.6 云层颜色不吃日落/天空色（`src/systems/weather.ts:28-29`）

```ts
const dark = clamp(params.exp - 0.5, 0, 0.55) / 0.55
cloudMat.color.setScalar(0.45 + 0.38 * dark)   // 恒为中性灰
```

云是 `MeshBasicMaterial`（不受光照，`fog:false`），颜色只由**曝光**推一个标量灰。于是"多云 + 日落"时天空是橙红、云是死灰，恰恰丢掉了 `docs/项目方案.md` 里强调的"冷暖对撞"这一记忆点。

修法：把 `params.sun`（或新加一个 `skyHorizon` 色）以低比例混进云色，例如 `color.copy(neutral).lerp(params.sun, 0.35)`；成本 0（本来每帧就在写）。

#### 4.7 环境烘焙"只节流、不落定补烘"，与文档承诺不符

`docs/项目方案.md:161` 承诺"过渡期 ≤ 3 次/切换（0.38s 节流 + **落定补烘**）"，但 `sky.ts:60-64` 只有节流：

```ts
refreshEnv(dt) { if (!dirty) return; timer += dt; if (timer >= ENV_INTERVAL) regen() }
```

`dirty` 在缓动期间每帧都会被置真（`sky.ts:52` 的比较阈值 `1e-8 / 1e-4` 远小于单帧变化量），所以一次交互后约 1.5s 内会连续烘焙 ~4 次，且**缓动结束后不会补一次"终值"烘焙**——如果最后一次采样刚好早于收敛点，环境贴图会停在一个中间态，直到下次参数变动才纠正。

建议：记录 `lastBakedParams`，在 `!dirty`（收敛）且 `lastBaked != current` 时补烘一次；顺带把烘焙成本从"拖动时长 × 2.6 次/秒"降到固定 1–2 次。

#### 4.8 键表三处并行，缺编译期约束

同一组键名要人工同步三份：

| 位置 | 内容 |
|---|---|
| `src/types.ts` `SceneParams` | 20 个字段（14 数值 + 6 颜色） |
| `src/core/interpolate.ts:5` `NUM_PARAMS / COL_PARAMS` | 参与轨道采样的 7 + 6 |
| `src/core/state.ts:72-79` `NumKey / NUM_ALL` | 参与 lerp/拷贝的 14 |

漏写一处不会报错，只会表现为"某参数永远不缓动/永远是 0"。目前靠 `params.test.ts` 的间接断言兜着（雾密度、半球光为正等），但新增一个参数时没有任何护栏。

建议（低成本、零运行时开销）：

```ts
type TrackedNum = 'rayleigh' | 'sunInt' | ... | 'folScale'
const NUM_PARAMS = ['rayleigh', ...] as const satisfies readonly TrackedNum[]
// 反向断言：NUM_PARAMS 的并集是否覆盖全部轨道键
type _Covered = Exclude<keyof SeasonTracks['num'], typeof NUM_PARAMS[number]> // 应为 never
```

#### 4.9 地面是半径 30 的圆盘，边界可能可见（待视觉确认）

`environment.ts:21,27` 两层 `CircleGeometry(30, 48)`，天空球 `scale 450`，相机 `far 2000`。`FogExp2` 的衰减是 `1 - exp(-(d·ρ)²)`：

| 场景 | `fogD` | 30 米处雾浓度 |
|---|---|---|
| 夏日正午（clear） | 0.002 | **0.36%** |
| 秋日正午（clear） | 0.008 | 5.7% |
| 冬季（clear） | 0.016 | 21% |
| 冬季雨 | 0.0288 | 54% |

即晴天正午地面边界基本"裸奔"，理论上会看到地面圆盘与远处天空球之间的一条硬边。因为相机 `maxPolarAngle = 0.49π`（几乎贴地）且 `maxDistance = 26`，这条边有没有进入画面需要截图确认——**建议实机截一张"夏·12:00·晴"的图**。若可见，修法按成本排序：把圆盘半径从 30 提到 60–80（顶点数不变，仍是 48 段）→ 加一圈垂直裙边下沉 → 让雾密度下限抬到 0.006。

#### 4.10 相机无键盘控制（WCAG 2.1.1）

`camera.ts:17-24` 只依赖 `OrbitControls`（鼠标/触控），`enablePan=false`。纯键盘用户完全无法改变视角。`docs/ui-qa-report.md` 已自认此项，但仍是当前最高优先级的**合规缺口**。低成本方案：方向上/下/左/右 + `+/-/=/- ` 直接改 `controls.target`/球坐标，或提供 4 个"视角预设"按钮（更好，兼顾可读性）。

#### 4.11 `tourPausedUntil = Infinity` 无超时兜底（`camera.ts:33-34`）

`start` 事件置 `Infinity`，只有 `end` 会恢复。指针捕获理论上保证成对，但窗口失焦、设备热插拔、多指手势中断都可能只收 `start`。一旦如此，巡游永久静默，且 UI 仍显示"开启"。建议加一个 `setTimeout`/帧内看门狗，或把 `Infinity` 换成"暂停至 now + 5s"。

#### 4.12 体积：单 chunk 556 kB

three + addons 全量入包，首屏 parse/执行成本高移动端明显。低成本改进：`build.rollupOptions.output.manualChunks = { three: ['three'] }`（让三方库长缓存），或把 `EffectComposer` 那条链改成动态 `import()` 让首帧更早出现（需处理首帧前后的渲染路径差异，收益中等）。

## 5. 性能剖析

### 5.1 每帧固定成本

| 项目 | 当前实现 | 评估 |
|---|---|---|
| 参数解析 | 7 数值 + 6 颜色轨道插值 | 微秒级，可忽略 |
| 缓动 | 14 次 `+=`、6 次 `Color.lerp` | 可忽略 |
| 阴影 | 2048² PCFSoft，**每帧重绘**（夜间也重绘） | 4.2 M 深度像素 + 全场景 draw call；P0-4.3 |
| 主渲染 | 1 次场景 pass | 基准成本 |
| Bloom | 全分辨率、5 级 mip、始终开启 | 1080p @ DPR 2 ⇒ 约 4 M 像素 ×（提亮 + 5 次降采样 + 5 次升采样），集显是主要瓶颈 |
| 输出 | `OutputPass`（tone mapping + sRGB） | 必要成本 |
| 粒子 | 单 `Points`，≤420 顶点 CPU 更新 | 可忽略 |
| 环境烘焙 | 脏时每 0.38s 一次 `pmrem.fromScene` | 拖动滑杆 ≈2.6 次/秒；P1-4.7 |

### 5.2 自适应 DPR 的实际效果边界（`loop.ts:29-46`）

- 触发条件：连续 90 帧 > 22ms（≈1.5s）才降一档 0.25，回升需连续 240 帧 < 15ms。**首次掉帧的用户体验前 1.5s 是全质量的**，移动端可能已经热到降频。
- 下限写死 `Math.max(1, dpr - 0.25)`：**DPR 永远 ≥ 1**，无法用"半分辨率 + 后处理"换取帧率。对集显/移动端这是最有效的一档，缺了。
- 只降分辨率、不降后处理：1080p 下 Bloom 仍在全分辨率跑。分级策略应是"先关/减 Bloom → 再降阴影尺寸 → 最后降 DPR"。

### 5.3 建议的性能分级（按投入产出）

1. **夜间关阴影**（1 行 + 阈值，立刻省 4.2 M/帧）—— P0。
2. **Bloom 分级**：`window.innerWidth * dpr < 900` 或首测帧率低时把 `UnrealBloomPass.resolution` 减半，或直接 `bloomPass.enabled = false`（`params.bloom < 0.02` 时本来就看不见，可据此跳过 —— 注意 `EffectComposer` 跳过 pass 仍需 `renderToScreen` 正确）。
3. **DPR 下限放到 0.75**，并允许阴影 1024 档。
4. **落定补烘**（P1-4.7），把拖动期间的烘焙从 n 次压到 1 次。

## 7. 可访问性详评

**做得好的**

- 语义结构：`<main aria-label>`、`role="group" aria-labelledby`、按钮一律 `type="button"` + `aria-pressed`，滑杆有 `aria-valuetext`。
- 读屏友好：语境短句与时间读数分离，只有前者 `aria-live="polite"`；拖动期间不重写文本节点（`hud.ts:115-121` 有显式判断）——这是很讲究的细节。
- `prefers-reduced-motion` 同时作用于 CSS 过渡与 JS 运镜（`camera.ts:27-28,58-62`）。
- `forced-colors: active` 用 `Highlight` 描边选中态（`style.css:425-431`），Windows 高对比模式可辨识。
- 12 个对比度断言 ≥ 4.5:1。

**缺口**

1. 相机无键盘/无"视角预设"（WCAG 2.1.1，4.10）。
2. 巡游按钮在 reduced-motion 下状态撒谎（4.2）。
3. 加载/失败状态无 `role="alert"` 的失败分支（4.4）。
4. 拖拽 3D 画布没有任何键盘等价物，也没有 `tabindex` 说明"这是可交互画布"。
5. `#loader` 的 `pointer-events: none` 让加载期间下层仍可点击（`style.css:131`）——目前无害，但若以后加"加载中禁用"逻辑会冲突。

## 9. 未验证项（需实机/视觉复核）

1. **地面圆盘边界是否可见**（4.9）——依赖实际构图与天空球下半球颜色，需截图确认。
2. **60fps @ 1080p 预算是否成立**（5.1）——需在目标设备上用 `renderer.info` 与 Performance 面板实测 draw call / 帧时。
3. **多云/雨天云层观感**（4.6）——颜色改动需人眼比对，不能只看数值。
4. **夜间阴影关闭后是否出现视觉回归**——理论上 `sunInt = 0` 时阴影不可见，但 Bloom 会让高亮像素"吃"到阴影边缘，需目视一次。
